**Product issue:** `#4 — [C46] Upgrade V1.0 runtime baseline to Node 24 LTS`

## 1. Test Lead decision

AtlasBadge V1.0 will not launch on the current Node 22 runtime baseline. The Test Lead requires a controlled migration to Node 24 LTS before the final V1.0 Release Candidate regression and before GO LIVE.

This is a deliberate pre-release runtime migration, not incidental environment maintenance.

## 3. Objective

Move the Product's supported runtime/build contract to Node 24 LTS using the smallest safe change while preserving functional behaviour and establishing a reproducible Node 24 Release Candidate baseline.

## 4. Scope

C46 includes only changes that are required for Node 24 qualification, such as:

- `package.json` Node engine contract;
- lockfile/npm metadata generated by the selected Node 24 LTS/npm pair;
- Vercel or runtime configuration only if the existing project does not select Node 24 correctly;
- narrowly required compatibility corrections discovered by evidence.

C46 does not authorize unrelated framework, Firebase, React, Playwright, Vitest, Tailwind, ESLint or application feature upgrades.

Any functional Product incompatibility found during qualification must be classified and handled as a separate bounded correction before continuing.

## 5. Risks

Primary risks:

- clean-install drift caused by npm major-version differences;
- lockfile normalization beyond the intended runtime migration;
- runtime/API behaviour differences between Node 22 and Node 24;
- Next.js or Firebase tooling incompatibility;
- Vercel build/runtime remaining on Node 22 despite local Node 24 qualification;
- stale green evidence being carried across a runtime boundary without impact analysis;
- broad dependency upgrade churn being hidden inside the runtime migration.

## 6. Mandatory controls

Apply at least:

- LL-01 — rerun only checkpoints invalidated by the runtime migration;
- LL-02 — state the invalidated checkpoint before selecting tests;
- LL-03 — use the smallest layer that can prove each affected boundary;
- LL-05 — finalize configuration/lockfile changes before final gates;
- LL-06 — account explicitly for untracked files;
- LL-11 — do not preserve stale automation at the expense of Product truth;
- LL-12 — do not weaken acceptance criteria to satisfy tooling;
- LL-16 — Emulator isolation must remain observable;
- LL-18 — publish evidence after the technical state is stable;
- LL-21/22/23 — identify effective backend/environment accurately;
- LL-66 — mandatory bounded agent preflight and stop rule.

## 7. Implementation contract

Default Product implementation agent: Antigravity.

The implementation must:

1. verify Product and Portfolio baselines;
2. inventory dirty/untracked state before mutation;
3. select one current Node 24 LTS patch and record its exact version/npm version;
4. update the Node engine contract from `22.x` to `24.x`;
5. reconcile the lockfile under Node 24 without unrelated dependency upgrades;
6. classify every material lockfile version change;
7. stop on unexpected dependency/version drift;
8. keep Firebase/backend configuration unchanged unless Node 24 requires an explicitly evidenced correction;
9. avoid commit/push/deploy until the coordinator reviews the candidate unless publication is separately authorized.

## 8. Minimum qualification gates

The Node 24 candidate must prove, as applicable:

```text
node --version
npm --version
npm ci
git diff --check
TypeScript
ESLint
full Vitest
geography validator
Firestore/Storage Rules suite
account-deletion gate when safe/applicable
production build
npm dependency-tree validation
```

Because the runtime boundary changes, affected browser/integration coverage must also include the permanent Emulator-backed Playwright suite or the subset selected by documented impact analysis. Emulator evidence must retain `realFirebaseRequests=0` when that observer is available.

## 9. Vercel qualification

A successful local build is not sufficient.

After publication authorization, C46 must prove that the Git-connected Vercel deployment:

- corresponds to the exact approved C46 SHA;
- is `READY`;
- targets Production or the explicitly selected release environment;
- actually builds/runs under Node 24 rather than silently retaining Node 22;
- does not require a manual Production configuration mutation that has not been recorded.

## 10. Exit criteria

C46 may be considered technically qualified only when:

- Node 24 LTS is the declared Product runtime contract;
- clean `npm ci` succeeds under the selected Node 24 runtime;
- dependency/lockfile review finds no unexplained version drift;
- affected static/unit/Rules/build/browser gates pass;
- the exact published SHA is deployed by Vercel and Node 24 runtime selection is evidenced;
- repository state is clean after publication;
- no open Node 24 compatibility blocker remains.

## 11. Relationship to final RC regression

The broad final V1.0 RC regression must occur **after** C46 qualification, because a major runtime change invalidates the previous final-RC entry assumption.

Historical feature evidence that does not materially depend on Node runtime may be carried forward under LL-01 after impact analysis; runtime/build/tooling/integration checkpoints affected by C46 must be requalified.

## 12. Release decision

Current decision:

**APPROVED TO START C46 / NOT YET READY FOR GO LIVE.**

The final V1.0 release still requires the post-C46 RC regression, mandatory Windows Google Chrome coverage, Production smoke, controlled Production data reset, clean-start verification, residual-risk/Test Summary reporting and explicit Test Lead GO LIVE approval.
